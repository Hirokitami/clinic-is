# ИС медицинской клиники — версия 2.0

Программная реализация командного проекта по «СРО общее (часть 2)»: сценарии С1–С11, 9 информационных
объектов и 8 справочников (СРО 10), 24 функции в 6 подсистемах (ПР 5), алгоритм записи на приём (СРО 11),
окна рабочего места врача (СРО 13), требования Т1–Т13.

- **backend/** — FastAPI + SQLAlchemy 2 + SQLite (через `CLINIC_DATABASE_URL` можно PostgreSQL), JWT в httpOnly-cookie, pytest.
- **frontend/** — Next.js 16 (App Router, TypeScript, Tailwind). Запросы `/api/*` проксируются на бэкенд.
- **legacy_flask/** — прежний прототип на Flask (версия 1.0), сохранён для сравнения.

## Запуск в Docker (рекомендуется)

```bash
docker compose up -d --build
```

| Что | Адрес |
|---|---|
| Приложение | http://localhost:3000 |
| API (Swagger) | http://localhost:8000/docs |
| PostgreSQL | localhost:5433, БД/пользователь/пароль `clinic` |

Демо-данные загружаются только в пустую базу, поэтому перезапуск контейнеров данные не стирает.
Сбросить базу к демо-состоянию: `docker compose down -v && docker compose up -d`.
Пароль БД и ключ токенов можно задать в `.env` рядом с `docker-compose.yml` (`POSTGRES_PASSWORD`, `CLINIC_SECRET_KEY`).

### Публичный доступ через Cloudflare Tunnel

```bash
docker compose --profile tunnel up -d
docker compose logs tunnel | grep trycloudflare     # публичный адрес https://….trycloudflare.com
docker compose stop tunnel                           # закрыть доступ из интернета
```

Quick Tunnel не требует аккаунта Cloudflare; адрес меняется при каждом перезапуске контейнера `tunnel`.
Перед открытием наружу смените демонстрационные пароли.

## Запуск без Docker

Нужны Python 3.11+ и Node.js 20+. Без Docker используется SQLite (`backend/clinic.db`).

```bash
# 1. Бэкенд (терминал 1)
cd backend
python -m venv .venv
.venv\Scripts\activate            # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python -m app.seed                # создать БД и демо-данные (повторный запуск пересоздаёт базу)
uvicorn app.main:app --reload --port 8000     # документация API: http://127.0.0.1:8000/docs

# 2. Фронтенд (терминал 2)
cd frontend
npm install
npm run dev                       # http://localhost:3000
```

Адрес бэкенда для фронтенда задаётся переменной `BACKEND_URL` (по умолчанию `http://127.0.0.1:8000`).
Настройки бэкенда — переменные `CLINIC_*` или файл `backend/.env` (см. `app/config.py`);
в рабочей среде обязательно задать `CLINIC_SECRET_KEY` и `CLINIC_COOKIE_SECURE=true`.

## Что изменилось по сравнению с версией 1.0 (СРО 15, «перспективы развития»)

| Было (частично / не выполнено) | Стало |
|---|---|
| Т4, Т5, Т6.1 — пациент не мог сам записаться и перенести запись | Самостоятельная запись, перенос и отмена в личном кабинете |
| У5 — не проверялась запись пациента на то же время к другому врачу | Проверка пересечения по времени при записи и переносе |
| Т10 — нет направлений и изменения приёма | Направления на исследования; изменение результатов приёма с историей (было → стало, автор, дата) |
| Учёт оказанных услуг не реализован | Услуги в окне приёма, цена фиксируется на дату оказания; суммы в отчётах |
| Результаты исследований вносились скриптом | Роль «Сотрудник лаборатории»: внесение результатов по направлениям |
| Расписание формировалось скриптом | Роль «Администратор»: рабочее время врачей и форма формирования расписания |
| Нет отчётов | Отчёты: загрузка врачей, неявки, обращаемость по специальностям, услуги |
| Т8 — SMS только как текст | Шлюз SMS — подключаемый модуль (`app/services/sms.py`); по умолчанию журнал «имитация отправки», сбой шлюза не отменяет запись (И8) |

Защита от наложения записей (Т5) — три уровня: повторное чтение интервала, условное `UPDATE … WHERE is_busy = 0`
в одной транзакции с созданием записи и уникальный частичный индекс `ux_appointment_active_slot`.

## Архитектура бэкенда

Модульный монолит: один модуль — одна функциональная подсистема ПР 5. Внутри модуля одинаковые слои:
`models.py` (таблицы) → `service.py` (бизнес-логика) → `router.py` (HTTP), `schemas.py` (схемы API).
Роутеры только принимают запрос и вызывают сервис; правила предметной области — в сервисах.

```
backend/app/
  core/             инфраструктура без предметной логики: config, db, errors, security (пароли, JWT),
                    clock (время клиники), numbering (номера Z-/P-/N-/U-/D-/L-ГГГГ-NNNNNN)
  modules/
    auth/           учётные записи, роли, вход; dependencies.py – current_user / require_roles (Т13)
    references/     8 справочников СРО 10
    patients/       электронная карта: регистрация, поиск (ИИН, ФИО + дата рождения), изменение
    schedule/       врачи, рабочее время, интервалы, формирование расписания, ближайшие свободные (А2)
    appointments/   запись / перенос / отмена / неявка – алгоритм СРО 11, блоки 1–12
    notifications/  SMS-подтверждения (подключаемый шлюз), журнал
    procedures/     назначения процедур и отметки выполнения (медсестра)
    lab/            направления на исследования и результаты (лаборатория)
    visits/         приём пациента, история пациента, изменение приёма с историей (врач)
    cabinet/        личный кабинет пациента
    reports/        отчёты администратора и показатели главного окна
  main.py           сборка приложения: подключает роутеры всех модулей
  seed.py           справочники и демо-данные (python -m app.seed [--if-empty])
```

Зависимости направлены в одну сторону: `core` ← `auth`, `references` ← `patients`, `schedule` ←
`appointments`, `notifications` ← `procedures`, `lab` ← `visits` ← `cabinet`, `reports`.
`tests/test_architecture.py` проверяет, что `core` не зависит от модулей и модули не импортируют чужие роутеры.
